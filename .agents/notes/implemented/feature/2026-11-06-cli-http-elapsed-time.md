# Agent Note: CLI HTTP 请求耗时

Status: implemented

## 问题

CLI 只有响应和保存路径，用户无法直接看到从 HTTP 发送到完成的等待时长。网页框选、GEC 准备和文件保存是其他阶段，不能混入请求耗时。

## 决策

generate 首次调用 fetch 前启动单调时钟，完整响应读取、连接释放及客户端校验结束后打印 `Request elapsed: 45.815s`。显式重试使用同一次总计时，包含重试间等待并显示实际发送次数。成功或失败均打印；发送前的 GEC 校验失败或捕获取消没有耗时输出。

计时由 requestGeneration 的可选同步回调返回给 CLI，响应对象和 response.json 不添加计时字段。时钟按调用注入用于测试，默认使用 performance.now，不改全局系统时间。[直接 HTTP 生成](../feature/2026-11-05-direct-http-generation.md)继续拥有协议、GEC 和重试规则，此处只扩展 CLI 显示，不修改 backend，也不取代其独立记录。

## 曾考虑的替代方案

**从命令启动计时。** 会混入浏览器启动、框选和 GEC 准备，不符合用户要求的 HTTP 等待时间。

**收到响应头就结束。** 不能包含完整响应体读取和校验，会低估用户实际等待。

## 验证

CLI 回归在新增实现前拒绝缺少计时回调和输出的状态。受控时钟证明首次 GEC 准备不计入、响应读取计入，重试仅输出一次总耗时，起始值为 0 也正确处理。真实 CLI 子进程的成功和 HTTP 503 均打印耗时，失败不宣称保存成功，发送前失败不打印。

`npm run test:cli` 的 35 项、直接捕获浏览器的 2 项、文档、Notes 和 diff 检查通过。临时服务器、子进程和浏览器均按测试拥有的资源等待退出，没有重放用户请求或调用真实模型。

## 后果

这是客户端的请求等待时长，不是 backend 模型或工具分段耗时；重试累计多个请求。输出增加一条诊断行，保持 HTTP 响应和保存文件的语义。
