# Agent Note: Widgee 生成布局的字号层次与空间利用

Status: implemented
Archived: 2026-11-05

## 问题

最新“天气小组件”会话的“晴雨之间”产物存在字体偏小、内容未充分利用画布的反馈。会话 `09856be9-f8f3-42a3-b18d-bca9b1bb2ee9`，修订 `e33890ff-6adb-46aa-8194-995595efa113` 使用 widgee-11。用户先要求天气 Widget，再明确增加紫外线、体感、风力等信息，不能通过删除这些要求来改善视觉。

源码将城市名设为 12pt、天气文字 11pt、页脚 9pt；中尺寸辅助指标为 11pt，大尺寸仅升到 12pt，未来天气仍为 10–11pt。温度为小 30pt、中 34pt、大 44pt。大尺寸与中尺寸共用主体行结构，只增加详情并将根 VStack 间距从 4pt 改成 7pt；固定外框使用 topLeading，没有分配主体、详情和页脚的剩余空间。未来预报缺失时还会减少行数而保持其余布局不变。

根背景已使用 context 外框与正负 14pt padding 配方，代码没有额外内缩背景。Chat 使用共享预览器按实际 Widget 尺寸排版，仅在显示容器较窄时整体等比缩小；这可能进一步影响观感，但不会制造内容内部的相对留白。修订后的产物由原生布局测量与 Chat 真机截图共同验证；高度检查不能独立证明横向文字完整。

[中尺寸内容预算](../../implemented/bug-fix/2026-10-20-widgee-medium-content-budget.md)有效防止超高，但教材的 compact typography 和以 caption 为主的示例对可读性、富余空间利用约束不足。该记录继续拥有防裁切决策，本记录补充字体层次与布局，不替代背景或预览一致性机制。

## 决策

微调原生 Widgee 的共享 WIDGET_GUIDE 与布局示例，常驻 prompt 和按需 widget 参考复用同一说明。先按实际内容区建立主数值、正文指标和辅助元信息的层次，再安排分组、行列与间距。普通字号下，正文与主要指标标签以 13–16pt 为起点，次要说明通常 11–12pt；主数值根据尺寸与信息量选择更大字号。数值仅为设计起点，不是所有内容与辅助字号的硬性下限；避免把 9–10pt 用作常规信息承载方式。

小、中、大分别组织内容。中尺寸利用额外宽度，把主数值与指标分区；大尺寸同时利用高度，提高主要信息和详情行的可读性，不只给中尺寸追加小字行。出现大片无信息空区时，先调整主内容尺度、分组和区块分配，再调整间距；保留必要呼吸空间，不通过巨型 Spacer、装饰或重复内容强行填满。背景继续铺满，宿主留白与真实 context 尺寸保持不变。

保留现有行高、间距和状态预算约束。空间不足时优先重排、精简重复标签；保留用户明确要求的字段，不能默认缩小所有字或截断关键值。预报缺失、加载、错误和待配置等状态使用独立的清楚构图，不以填满比例要求少量状态文字占据整个画布。

提示词版本为 widgee-12，兼容升级范围与产物边界由 [Widgee 协议](../../../../docs/widgee-protocol.md)维护，SDK API 不变。原天气会话保留布局修订，地点配置、storage 键、天气获取、缓存和刷新策略保持有效；历史与已采用版本不自动覆盖，用户预览后决定采用。

## 曾考虑的替代方案

**只放大当前天气脚本的字体。** 能改善单个结果，但不能影响后续生成；直接增大每一行还可能重新造成中尺寸裁切。

**调整宿主边距或全局缩放预览。** 会影响其他已生成 Widget，不能解决脚本中 9–12pt 的信息层次和大尺寸布局不足。

**统一规定最小字号或固定填充比例。** 不同信息量、长文本与状态页需要不同取舍，机械铺满会制造无意义的留白拉伸或装饰。采用可读字号起点、真实内容预算与截图评审。

## 验证

2026-10-21，后端 Widgee 测试 29 项、真实 pi 工具与教材测试 3 项通过，覆盖可执行示例、常驻与按需参考一致性、旧提示词版本升级及未知版本拒绝。Swift SDKTeachingTests 7 项通过，包含本轮真实生成的源码；类型检查、Swift strict lint、SDK、iOS 静态门禁、文档与 Notes 检查通过。

在 iPhone Air（iOS 27.0.1）运行 WidgetLayoutTests 与 WidgetBackgroundTests 共 6 项通过：教材覆盖 15 个尺寸与状态组合，超高布局、9pt 正文和内缩背景对照均被对应断言拒绝。生成产物通过显式传入合成状态，覆盖三种尺寸与正常、长值、无预报、加载、错误、配置六种状态，共 18 个组合；这部分替换启动取数，不读写用户业务数据。测试入口见 [iOS README](../../../../ios/README.md#真机聊天生成测试)。

真实模型在原会话生成修订 `3a1614c1-7106-4028-9511-66f64f11ede5`。AST 提取比较确认 initialState、onAppear、render、配置与取数函数、存储键逐字不变，仅 widget 和其布局 helper 改动。真机实测内容区小/中高度约 144.7pt、大高度 354pt；正常态自然内容高度分别为 129pt、120pt、342.7pt，无预报大尺寸为 291pt。截图检查了三尺寸、长地点、负温度、高风速、无预报及教材长数值，正文和页脚完整；这些数据是合成布局样本。

ChatLayoutE2ETests 在原会话切换小、中、大全部通过，使用已保存的北京市配置和真实预览路径，截图显示新修订、天气指标与页脚。没有采用产物或替换桌面实例。布局附件位于本机 `/tmp/widgee-readable-attachments`，Chat 截图位于 `/tmp/widgee-readable-ui-attachments`；对应 XCTest 结果含原始附件。

同一 gpt-6.1-sol、用户问题与工具定义的真实网关请求，首轮输入从 10,154 增至 10,531 tokens，增加 377（约 3.7%）。这是模型上下文成本测量，不代表生成成功率。

## 后果

教材同时约束防裁切和可读性，大尺寸不再只有追加小字行的示范。代价是增加上下文与原生视觉检查；机械高度和字号断言仅约束教材，任意生成脚本仍需截图评审。必要留白不是缺陷，少量状态文字也不强行铺满。

提高字号可能暴露横向溢出，因此修订配合分组和长值验证，不全局缩放已有 Widget。天气取数及数据含义没有调整，本轮不重新验收天气指标的正确性、桌面刷新或辅助字号；旧已采用版本仍须用户显式更新。网页转 Widget 的独立提示词不受影响。
